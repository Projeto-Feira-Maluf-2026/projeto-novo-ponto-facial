# ⚠️ REGRA PRINCIPAL

Este é um sistema de bate-ponto REAL.

O ambiente real NÃO terá:

* câmera perfeita;
* iluminação perfeita;
* funcionário perfeitamente parado;
* rosto sempre frontal;
* pessoa sempre próxima;
* imagem sempre em alta resolução.

O sistema precisa ser projetado pensando exatamente no contrário.

Teremos situações como:

* webcam simples;
* câmera de segurança;
* câmera IP;
* compressão de vídeo;
* rosto distante;
* rosto pequeno dentro do frame;
* iluminação irregular;
* pessoa andando;
* motion blur;
* ângulos diferentes;
* pessoa olhando ligeiramente para baixo;
* pessoa olhando para os lados;
* pequenas alterações de aparência;
* vários funcionários passando pela câmera.

Portanto:

**NÃO DESENVOLVA O RECONHECIMENTO PENSANDO EM UMA FOTO FRONTAL PERFEITA.**

Desenvolva pensando em uma câmera instalada em uma empresa.

# 2. PROBLEMA ATUAL GRAVE

Atualmente o sistema apresenta um problema inaceitável:

**às vezes nem eu mesmo consigo ser reconhecido estando próximo da câmera.**

E isso acontece mesmo depois de conseguir concluir o cadastro.

Portanto existe provavelmente algum problema envolvendo uma ou várias destas áreas:

* qualidade do cadastro;
* embeddings ruins;
* detector;
* alinhamento;
* crop;
* preprocessing;
* comparação;
* threshold;
* normalização;
* resolução;
* diferenças entre pipeline de cadastro e reconhecimento;
* seleção ruim dos frames;
* baixa diversidade das amostras cadastradas.

INVESTIGUE.

Não tente mascarar o problema simplesmente aumentando a tolerância.

---

# 3. PROBLEMA MUITO GRAVE NO CADASTRO

O cadastro facial atual também está ruim.

Hoje o sistema solicita movimentos/posições do rosto durante o cadastro.

Mesmo executando corretamente os movimentos solicitados, pode levar aproximadamente **3 MINUTOS PARA CONSEGUIR CADASTRAR CADA IMAGEM/ETAPA**.

Isso é completamente inviável.

Imagine cadastrar:

50 funcionários.

100 funcionários.

300 funcionários.

O cadastro precisa ser rápido, intuitivo e confiável.

E existe um problema ainda pior:

**depois de passar vários minutos cadastrando corretamente, o sistema pode não reconhecer aquela mesma pessoa.**

Isso indica que o fluxo atual precisa ser profundamente investigado.

# 4. RECONSTRUA A EXPERIÊNCIA DE CADASTRO

Quero um método de enrollment/cadastro facial muito melhor.

Não quero obrigatoriamente:

"olhe exatamente para esquerda"

aguardar...

"olhe exatamente para direita"

aguardar...

"olhe para cima"

aguardar...

durante vários minutos.

Crie um sistema inteligente de **captura automática de múltiplas amostras**.

Quando o funcionário posicionar o rosto diante da câmera, o sistema deve analisar continuamente os frames.

Durante poucos segundos, obtenha automaticamente boas representações daquela pessoa.

Por exemplo:

FRAME 1
FRAME 2
FRAME 3
...
FRAME N

Analise:

* nitidez;
* tamanho do rosto;
* iluminação;
* confiança da detecção;
* pose;
* yaw;
* pitch;
* roll;
* landmarks;
* oclusão quando disponível;
* diversidade em relação às amostras já selecionadas.

Não salve simplesmente vários frames praticamente iguais.

Selecione automaticamente um conjunto pequeno de **boas e diferentes representações do funcionário**.

Exemplo conceitual:

frontal
↓
levemente esquerda
↓
levemente direita
↓
outra variação útil

O funcionário NÃO deve precisar acertar uma posição perfeita por vários segundos.

Use tolerâncias realistas.

# 5. CADASTRO DEVE SER RÁPIDO

Objetivo:

Transformar o cadastro de algo que atualmente pode levar minutos em uma experiência que normalmente leve **poucos segundos**, desde que existam frames suficientes e adequados.

Não force artificialmente um tempo específico se isso comprometer segurança.

Quero algo semelhante a:

Funcionário posiciona o rosto.

Sistema começa automaticamente.

"Detectando rosto"

↓

"Capturando amostras"

↓

indicador de progresso

↓

"Cadastro concluído"

O sistema deve escolher os melhores frames automaticamente.

Se determinada amostra estiver ruim:

**não reinicie o cadastro inteiro.**

Continue capturando até conseguir substituí-la.

# 6. MÚLTIPLOS EMBEDDINGS POR FUNCIONÁRIO

Investigue como o sistema atualmente representa uma pessoa.

Caso exista apenas um embedding, considere seriamente alterar isso.

Cada funcionário pode possuir múltiplas representações.

Por exemplo:

Employee

→ embedding A
→ embedding B
→ embedding C
→ embedding D
→ embedding E

Esses embeddings devem representar pequenas variações reais.

Durante o reconhecimento, utilize uma estratégia matematicamente coerente para comparar o rosto detectado contra as representações daquela identidade.

Não simplesmente faça uma gambiarra como:

"se qualquer embedding ficar vagamente próximo, aceite".

Precisamos melhorar recall **sem destruir precisão**.

# 12. RECONHECIMENTO TEMPORAL

Vídeo possui uma vantagem enorme:

**temos vários frames.**

Use isso.

Não trate câmera como se fosse uma sequência de fotografias completamente independentes.

Quando detectar uma pessoa, acompanhe aquela face durante uma pequena janela temporal.

Conceitualmente:

DETECTAR

↓

TRACK ID

↓

FRAME 1 → score

FRAME 2 → score

FRAME 3 → score

FRAME 4 → score

↓

AGREGAÇÃO

↓

DECISÃO

Uma pessoa andando pode produzir:

frame ruim
frame ruim
frame excelente
frame bom
frame excelente

Não quero que o primeiro frame ruim determine tudo.

Da mesma maneira, uma correspondência suspeita em apenas um frame não pode bater ponto para a pessoa errada.

* estabilizar resultado;
* aumentar FPS.

Mas escolha uma implementação compatível com a arquitetura atual.

# 1. REMOVER O "VISUAL DE IA"

Procure especificamente pelos seguintes padrões.

## Cards em excesso

Um dos maiores sinais de UI genérica é transformar absolutamente tudo em cards.

Exemplo do problema:

Página → container → card → card interno → informação.

Isso fragmenta demais a interface.

### Melhorar

Use cards apenas quando representam objetos ou grupos realmente independentes.

Para informações relacionadas, prefira:

* agrupamento por proximidade;
* divisores sutis;
* mudança de espaçamento;
* hierarquia tipográfica;
* backgrounds de seção;
* alinhamento;
* grids;
* tabelas;
* listas estruturadas.

Nem toda informação precisa de:

`background + border + border-radius + shadow + padding`.

# 2. EVITAR O "CARD DENTRO DE CARD"

Não criar vários níveis de caixas arredondadas.

Evitar:

* container arredondado;
* dentro dele outro container arredondado;
* dentro dele três cards;
* dentro dos cards pequenos badges;
* tudo com borda.

Isso cria aparência artificial e excessivamente modular.

Use espaço vazio e hierarquia para separar conteúdo.

# 3. PARAR DE USAR BORDER-RADIUS EXAGERADO

Não aplicar `rounded-xl`, `rounded-2xl` ou `rounded-3xl` automaticamente em tudo.

Exemplo conceitual:

* controles pequenos → radius pequeno;
* inputs → radius moderado;
* cards → radius moderado;
* modais → radius maior;
* elementos especiais → radius próprio.

Não transforme cada elemento da aplicação em uma cápsula.

# 5. EVITAR GRADIENTES GENÉRICOS

ícone search → campo de pesquisa.

card compacto → painel detalhado.

O objetivo é fazer o usuário entender visualmente de onde veio o novo elemento.

---

# 51. SCROLL

Se houver páginas longas, utilizar scroll para melhorar contexto.

Possibilidades:

* headers sticky;
* filtros sticky;
* progress discreto;
* elementos que ganham/retiram elevação durante scroll;
* seções que revelam controles quando necessário.

Evitar parallax exagerado.

---

# 52. SCROLL-DRIVEN EFFECTS

Se fizer sentido, determinados elementos podem reagir ao scroll.

Utilizar apenas propriedades eficientes como:

transform

opacity

clip-path quando performático.

Evitar animações pesadas que prejudiquem FPS.

---

# 53. TOOLTIP

Tooltips devem possuir:

* pequeno delay;
* entrada curta;
* posicionamento correto;
* saída rápida;
* conteúdo realmente útil.

Não criar tooltip explicando coisas óbvias.

---

# 54. SKELETON INTELIGENTE

O skeleton deve representar aproximadamente o layout real que aparecerá.

Não colocar três retângulos aleatórios piscando.

---

# 55. FEEDBACK VISUAL IMEDIATO

Toda ação precisa responder rapidamente.

Ao clicar em algo, o usuário deve perceber imediatamente que sua interação foi registrada.

Mesmo se o backend demorar, a UI deve fornecer feedback visual.

---

# 56. ANIMAÇÕES BASEADAS EM FÍSICA

Quando a stack permitir, utilize springs cuidadosamente configuradas para determinados movimentos.

Especialmente:

* drawers;
* rearranjo de listas;
* indicadores;
* elementos arrastáveis;
* pequenas expansões.

Não utilizar bounce exagerado.

---

# 57. EASING

Evitar `transition-all duration-300 ease-in-out` em absolutamente tudo.

Definir curvas específicas para:

entrada;

saída;

movimento;

expansão;

microinterações.

Movimentos diferentes possuem comportamentos diferentes.

---

# 58. PERFORMANCE DAS ANIMAÇÕES

Priorizar:

`transform`

`opacity`

e propriedades que não causem layout/repaint pesado.

Evitar animar propriedades caras constantemente.

Manter a experiência fluida mesmo em computadores medianos.

---

# 59. PREFERS-REDUCED-MOTION

Respeitar:

`prefers-reduced-motion`.

Animações não podem prejudicar acessibilidade.

Criar fallback reduzido quando necessário.

---

# 60. RESPONSIVIDADE REAL

Não quero apenas:

desktop → diminuir tudo → mobile.

Repense a composição.

Desktop pode possuir:

sidebar + conteúdo + painel contextual.

Tablet:

sidebar compacta + conteúdo.

Mobile:

navegação própria + conteúdo prioritário.

A arquitetura pode mudar conforme o espaço disponível.

---

# 61. MOBILE NÃO É DESKTOP ESPREMIDO

No mobile:

* aumentar áreas clicáveis;
* reduzir informação simultânea;
* reorganizar ações;
* utilizar bottom sheets quando apropriado;
* manter ações importantes acessíveis;
* evitar tabelas impossíveis de utilizar.
