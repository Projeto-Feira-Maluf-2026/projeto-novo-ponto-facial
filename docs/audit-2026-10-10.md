## A. Diagnóstico original e fluxo

| Camada | Implementação encontrada |
|---|---|
| Web | React 18, TypeScript, Vite, MediaPipe, Supabase Auth, Axios |
| API principal | FastAPI leve em Vercel, SQLAlchemy async, PostgreSQL/Supabase |
| API facial | FastAPI em container, InsightFace/ArcFace buffalo_l, ONNX Runtime |
| Identidade | Embeddings 512-D, até cinco templates por identidade, margem entre candidatos |
| Persistência | PostgreSQL, migrations SQL versionadas, RLS bloqueando Data API |
| Complementos | SMTP/Brevo, Vercel Blob para fotos, Redis opcional, cliente Flutter |

1. Web obtém sessão Supabase; API valida token e papel de `app_metadata`.
2. `CameraCapture` abre `getUserMedia`, carrega MediaPipe, detecta/tracks rostos
   e mantém evidência temporal. Captura é interrompida em pausa/aba oculta.
3. Terminal recorta e envia imagens JPEG à API facial, em lote de até cinco rostos.
4. Servidor valida/decodifica imagem, detecta/alinha, extrai embeddings com modelo
   versionado; escala e enhancement são adaptativos. Enhancement localiza, mas
   pixels originais alimentam a identidade.
5. Frames utilizáveis e coerentes compõem consulta; templates elegíveis são
   limitados por qualidade, versão, identidade e vínculo ativo com a obra.
6. Matching usa centróide ponderado, mediana de scores e margem do segundo candidato.
7. Servidor bloqueia linha do funcionário antes de consultar duplicata e sequência;
   persiste registro/auditoria, confirma transação e envia notificação.
8. Web só confirma quando recebe `record.id` e `record.occurred_at` persistidos.

Cadastro usa sessão persistida, amostras provisórias, qualidade/diversidade e
ativação transacional de templates. Documentação existente descreve câmera,
cadastro, healthchecks e armazenamento de horários UTC/exibição São Paulo.
Isso não constitui prova de operação real de todos esses componentes.

## B. Riscos priorizados e alterações

| Prioridade | Evidência original | Correção/estado |
|---|---|---|
| P0 | `auth.py` e `permissions.ts` aceitavam `user_metadata.role` | Papel somente de `app_metadata`; testes negativos |
| P0 | `attendance.py` autorizava embedding direto e usava qualidade do cliente | Somente imagem processada no servidor contribui para reconhecimento/confiança |
| P0 | Funcionário tinha scope de correção e histórico global | Scope `attendance:correct` separado; funcionário sem leitura global enquanto faltar vínculo confiável |
| P1 | NaN/Inf podia virar score máximo | Validação finita, dimensional e de norma; templates inválidos descartados |
| P1 | Retry podia ocultar erro de runtime ou múltiplos rostos | Falha indisponível e múltiplos rostos preservados em todas etapas |
| P1 | `employee_id` pulava filtro de obra | Associação ativa de obra aplicada também na identificação explícita |
| P1 | Dispositivo recebido não era validado | Dispositivo informado deve existir, estar ativo e pertencer à obra |
| P1 | Concorrência podia duplicar/alterar sequência | Row lock PostgreSQL por funcionário e replay de `offline_batch_id` |
| P1 | JWT expirado/cache stale ainda autorizavam | Expiração antes do cache; outage não amplia stale grace |
| P1 | Terminal fabricava ID/data quando record ausente | Confirmação depende de registro do servidor; respostas canceladas descartadas |
| P1 | Cache de leitura sobrevivia à troca de usuário | Invalidação por geração de sessão e descarte de resposta antiga |
| P1 | CSV/XLSX interpretavam texto como fórmula | CSV neutraliza prefixos; XLSX declara célula textual |
| P1 | PDF cortava após 200 registros | Exportação inclui todos os registros retornados pela consulta |
| P1 | Ambiente Windows limpo falhava com São Paulo | `tzdata` declarado nos manifests e lock |
| P2 | play/enumerate/detector após unmount publicavam recursos | Guards de ciclo de vida e descarte do detector tardio |
| P2 | Captura podia enviar frame indisponível/congelado | Exige frame atual e track live/não mudo |
| P2 | CI ignorava testes web e lock Python; Node incompatível | uv locked, testes web, Node 24, permissões mínimas, cancellation |
| P2 | Locks npm divergentes | Lock raiz canônico; lock web redundante removido |
| P2 | Docker web Node 20/npm install | Node 24/npm ci/contexto raiz; dockerignore exclui segredos/caches |
| P3 | Chunk Three.js acima de 500 kB | Aviso preexistente documentado; sem mudança estética ou split não medido |

`npm ci --ignore-scripts` na raiz passou após consolidar lock.
Scan limitado de padrões conhecidos em arquivos rastreados não encontrou
segredos; não substitui secret scanner completo nem auditoria do histórico/bundle.
pip-audit do lock base+dev: 61 dependências, zero vulnerabilidades conhecidas
reportadas; extras InsightFace/ONNX não fazem parte dessa execução.
`npm audit`: 14 entradas (9 high) antes → 7 (5 high, 2 moderate) depois.
`npm audit --omit=dev`: zero entradas na árvore instalada de produção.
As sete restantes pertencem à cadeia Tailwind/build; não tratamos isso como
prova de exploit no site, mas o gate de dependências permanece pendente.

Benchmark local do coordenador: seed 20261010, vetores sintéticos float32 de
512 dimensões, cinco templates por identidade, mediana de sete repetições,
mesmo processo Python 3.12 e hardware. Código baseline carregado via Git,
sem alterar checkout; código atual comparado no mesmo processo.

|---|---:|---:|---:|

ataques de apresentação, aparência/iluminação/dispositivos e diferenças de
desempenho entre populações. Não houve uso de rostos reais ou envio externo
de biometria. A proteção numérica melhora casos inválidos específicos; não
permite concluir aumento da precisão biométrica geral.

## F. Riscos restantes e plano priorizado

1. **P1, impacto alto:** falta PAD integrado e desafio anti-replay confiável.
   Imagem submetida pelo cliente ainda pode ser fotografia/vídeo/injeção.
   Exigir protocolo e dataset autorizado antes de homologar; oferecer alternativa
   auditável aprovada pelo responsável, sem afirmar que piscada resolve spoofing.
2. **P1, impacto alto:** falta associação auth-user→funcionário/obras.
   Gestores/supervisores ainda têm leituras/mutações globais. Projetar vínculo,
   migration e testes negativos de escopo antes de disponibilizar a multiempresa.
3. **P1:** timestamp/tipo offline continuam campos recebidos. Política de jornada,
   horário servidor, limites offline e autenticação de dispositivo precisam
   decisão de domínio; não inventamos regras. Cooldown depende do prefixo terminal.
4. **P1:** templates LargeBinary não são cifrados pela aplicação; proteção de
   storage/key management, retenção/exclusão, finalidade/base legal/RIPD quando
   aplicável, e licença comercial buffalo_l precisam evidência operacional.
5. **P1:** executar concorrência/falha/rollback em PostgreSQL isolado e definir
   backup com ensaio de restauração; idempotência exige ID do cliente estável.
   Cache positivo de autorização ainda dura até 60 s; JWT local depende de exp.
6. **P2:** fila Flutter shared_preferences pode perder novo item durante sync
   concorrente e guarda payload local. Cliente é protótipo; sem build Flutter,
   testes de durabilidade, cifragem e limites de retenção nesta sessão.
7. **P2:** Docker root, portas Compose públicas, ausência de limites CPU/RAM/PIDs,
   capabilities/no-new-privileges e base digests. Dockerfile API local/setup ainda
   usam pip ranges; instalar por lock e testar imagem antes de alterar execução.
   Docker indisponível aqui; imagem web atualizada não foi construída.
8. **P2:** sete advisories do build Tailwind exigem migração compatível planejada;
   actions ainda por tags, sem SAST/CodeQL/secret scanning automatizados.
9. **P2:** geração de relatório permanece síncrona, intervalo sem limite e leitura
   completa em RAM; PDF ainda corta texto longo em 140 caracteres por linha.
   Worker/paginação e layout devem ser medidos antes de expandir operação.
10. **P2:** MediaPipe no main thread; testar Worker, limites de concorrência ONNX,
    cache autorizado de templates e vetorização com benchmark de resultado exato.
11. **P2:** logs estruturados/redação, métricas de duração/p95/saturação, alertas
    por impacto e runbooks detalhados ainda precisam implementação operacional.
12. **P3:** revisar teclado, leitores de tela, viewports reais, câmera física e
    Three.js. Sem inspeção visual/responsiva nesta sessão; identidade preservada.

## G. Rollback e gates

Sem schema alterado: reverter cada conjunto de diffs, restaurar lock compatível
e reinstalar dependências. Não usar git reset/restore indiscriminadamente sobre
trabalho futuro do usuário. Não reverter proteções de autorização/biometria em
produção sem mitigação: o código antigo contém falhas demonstradas.

Antes de release: testar migration futura em staging, concorrência PostgreSQL,
E2E autorizado com câmera real, precisão/PAD por protocolo representativo,
segredos/bundle/dependências, licença, backups/restauração e escopo de usuários.
Depois de release autorizado: exigir ambas APIs prontas, `/health/live`,
`/health/ready`, capacidades faciais, login, cadastro, batida persistida,
replay e relatório; comparar build id, erros e latência. Manter release anterior
compatível, suspendendo biometria se PAD/modelo/configuração falharem.

Missão completa de produção permanece **parcial** por ausência de dataset
autorizado, hardware/câmera de referência, ambiente PostgreSQL isolado e Docker,
além das decisões de domínio/licença/privacidade acima. A etapa local de correções
e testes não deve ser confundida com certificação de produção.
