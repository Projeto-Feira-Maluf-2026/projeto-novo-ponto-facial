## Diagnóstico e evidências

### P1 confirmado: API de produção não inicializava

Consultas HTTP sem autenticação ao domínio `curitiba-gestao.vercel.app`:

| Rota | Resultado anterior à correção local |
|---|---|
| `/login` | 200, HTML |
| `/api/health/live` | 500, `FUNCTION_INVOCATION_FAILED` |
| `/api/health/ready` | 500, `FUNCTION_INVOCATION_FAILED` |
| `/api/v1/dashboard` | 500, `FUNCTION_INVOCATION_FAILED` |

Os logs de runtime da Vercel apontaram `ValidationError` durante a importação de
`api/index.py`, em `Settings`: `Staging e production exigem origens CORS HTTPS`.
A configuração remota tinha `ENVIRONMENT=production` e uma lista CORS contendo
origens HTTP loopback de desenvolvimento e origens HTTPS. Não era falha de
build: a Function não chegava a iniciar.

### P1 confirmado em teste: indisponibilidade de Auth provocava logout

`AuthService.authenticate` transformava qualquer resposta HTTP diferente de 200
do Supabase em `PermissionError`, posteriormente convertida em 401 pela API.
O interceptor do frontend apaga a sessão local ao receber 401. Assim, 429 e 5xx
do provedor eram tratados como credencial inválida.

### Riscos ainda não validados

- **P1:** esta base exige Redis distribuído para mutações em produção. Se Redis
  estiver indisponível, as gravações retornam 503 deliberadamente. O endereço
  secreto do Redis não pôde ser exportado pelo CLI; não foi presumido saudável.
- **P1:** o código mantém bloqueio biométrico em produção quando PAD/calibração
  não estão disponíveis. Não foi desativado para contornar indisponibilidade.
  O serviço facial remoto respondeu readiness 200, mas declarou ambiente
  `development`; isso não demonstra prontidão biométrica de produção.
- **P2:** warning preexistente de chunk 3D acima de 500 kB no frontend.

## Plano executado e alterações

1. Reproduzir a configuração problemática em testes isolados, sem `.env` real.
2. Validar primeiro a sintaxe das origens. Em staging/production, descartar da
   allowlist apenas HTTP com host exato `localhost`, `127.0.0.1` ou `::1`.
   Origens HTTP externas, curingas, caminhos, credenciais e regex continuam
   recusados. O próprio `FRONTEND_URL` continua exigindo HTTPS.
3. Tratar 408, 429 e 5xx do Supabase como `AUTH_PROVIDER_UNAVAILABLE`/503, sem
   autorizar acesso, reutilizar autorização expirada ou expor resposta interna.
   Respostas de rejeição da sessão continuam negadas.
4. Adicionar teste de cold start em outro interpretador, com `VERCEL=1`, ambiente
   production e a allowlist mista. O teste inicia lifespan, verifica liveness
   JSON 200 e exige JSON 401 nos cadastros/dashboard sem token. Importações de
   NumPy, OpenCV, InsightFace e ONNX são bloqueadas para reproduzir a Function
   leve. Pillow permanece permitido: já integra o runtime de fotos/relatórios.

Arquivos: `api/app/core/config.py`, `api/app/services/auth.py`,
`tests/test_cors_startup_regressions.py`, `tests/test_supabase_auth.py` e
`tests/test_face_provider_safety.py`.

## Preparação da publicação autorizada

Após o diagnóstico, o responsável autorizou commit, integração em `main` e
publicação, preservando deployments anteriores. Foi constatada uma divergência:
o branch de produção configurado na Vercel era `main`, mas o deployment servido
pelo domínio principal apontava para `ultima-versao` (`10beb22`).

Para reduzir novas divergências:

- `main` volta a ser a referência canônica de publicação, por integração normal
  no Git, sem force-push e sem apagar branches de trabalho.
- `installCommand: npm ci` torna explícita a instalação pelo lockfile na Vercel.
- Materiais de contexto/prompt e lockfile de skills locais ficam fora do upload.
  `skills-lock.json` foi preservado no disco, mas ignorado pelo Git.
- Deployments anteriores são preservados para rollback; cache de build pode ser
  ignorado em um novo deploy, sem destruir fontes ou dados persistentes.
- Verificação repetida antes do commit: Ruff OK, **311 testes Python aprovados,
  1 ignorado**, **99 testes frontend aprovados**, TypeScript/build OK. O warning
  preexistente de bundle 3D permanece.

Esta seção registra a preparação, não confirma um deploy concluído. A verificação
de publicação e as dependências externas precisam ser avaliadas após o release.
