## 1. Sessão: queda de rede não pode apagar o login salvo

- **Problema:** na abertura do app, timeout ou falha de rede em `getSession`/`getUser`
  executava `signOut({ scope: 'local' })`, apagando os tokens salvos do tablet/terminal
  e mostrando o login sem explicação.
- **Fontes:**
  - Supabase, `auth.getUser()`: "This method performs a network request to the Supabase
    Auth server" — <https://supabase.com/docs/reference/javascript/auth-getuser>
  - Código do cliente `auth-js`: falha de `fetch` vira `AuthRetryableFetchError` com
    status `0`; 502/503/504 também viram `AuthRetryableFetchError`; os demais erros viram
    `AuthApiError` com o status HTTP —
    <https://github.com/supabase/auth-js/blob/master/src/lib/fetch.ts> e
    <https://github.com/supabase/auth-js/blob/master/src/lib/errors.ts>
- **Decisão:** só 400/401/403/404/422 descartam a sessão. Status 0, 408, 429, 5xx e
  timeout mostram o estado "serviço de login indisponível", mantêm os tokens e
  oferecem "Tentar novamente" e "Entrar com outra conta".
- **Alternativas:** usar `isAuthRetryableFetchError` do SDK (não cobre 500 nem o nosso
  timeout local); renderizar rotas protegidas com sessão não verificada (rejeitado:
  o servidor recusaria tudo e a tela ficaria inconsistente).
- **Trade-off:** um 500 persistente do Auth deixa o usuário na tela de indisponível
  até ele escolher "Entrar com outra conta", em vez de cair direto no login.
- **Aceitação:** `web/src/auth/AuthContext.test.tsx` (novos casos) e roteiro em
  navegador real descrito no relatório da rodada.

## 2. Câmeras: endereços alternativos e DNS que apontam para a própria API

- **Problema:** `127.1`, `2130706433`, `0x7f000001`, `017700000001` e
  `::ffff:127.0.0.1` passavam pela validação de host da câmera, embora o resolvedor
  do sistema/FFmpeg os trate como 127.0.0.1. Um nome DNS também podia resolver para
  loopback ou metadata.
- **Fontes:**
  - OWASP SSRF Prevention Cheat Sheet: testar codificações "Hex, Octal, Dword, URL and
    Mixed"; "A second, unchecked DNS lookup between validation and connection can bypass
    these checks"; "Deny-lists are bypass-prone. Prefer allow-lists." —
    <https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html>
  - Python `socket.inet_aton`: "also accepts strings with less than three dots" e a
    validade depende do `inet_aton` da libc —
    <https://docs.python.org/3/library/socket.html#socket.inet_aton>
- **Decisão:** recusar no schema qualquer host que `inet_aton` aceite mas que não seja
  IPv4 canônico; desembrulhar IPv6 mapeado para IPv4; bloquear também `0.0.0.0/8` e
  `fd00:ec2::254`. Antes de abrir o stream, resolver o nome e recusar se qualquer
  endereço resolvido for loopback, link-local, multicast, não especificado ou metadata.
- **Aplicabilidade local:** câmeras IP vivem em faixas privadas, então RFC 1918/ULA
  continuam permitidas (allowlist por rede exigiria cadastro do owner).
- **Risco residual:** o OpenCV/FFmpeg resolve o nome de novo ao conectar (TOCTOU,
  DNS rebinding). Fixar o IP na URL quebraria RTSPS/HTTPS. Próximo passo sugerido:
  `CAMERA_ALLOWED_NETWORKS` por obra. A gravação de câmeras exige `devices:write`
  (somente `SUPER_ADMIN`), o que limita a exposição.
- **Aceitação:** testes parametrizados em `tests/test_data_integrity_and_cameras.py`.

## 3. Horários exibidos em São Paulo independentemente do aparelho

- **Problema:** o README promete exibição em `America/Sao_Paulo`, mas todos os
  formatadores do frontend usavam o fuso do aparelho, e o período de relatórios usava a
  meia-noite local do navegador.
- **Fonte:** MDN, `Intl.DateTimeFormat`: o padrão de `timeZone` "is the runtime's time
  zone" —
  <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat/DateTimeFormat>
- **Decisão:** `formatInAppTimeZone`, `appDateInput`, `shiftDateInput` e
  `appDayBoundaryIso` em `web/src/utils/dateTime.ts`, usando a base IANA do navegador
  (sem `-03:00` fixo, para continuar correto se o horário de verão voltar).
- **Alternativa:** `date-fns-tz` (dependência nova; rejeitada porque `Intl` resolve).
- **Aceitação:** `web/src/utils/dateTime.test.ts`, executado com `TZ=UTC`, `Asia/Tokyo`,
  `America/Manaus`, `America/Sao_Paulo` e `Pacific/Kiritimati`.

## 4. `datetime.utcnow()`

- **Fonte:** "Deprecated since version 3.12: Use `datetime.now()` with `UTC` instead." —
  <https://docs.python.org/3/library/datetime.html#datetime.datetime.utcnow>
- **Decisão:** `as_utc_naive(datetime.now(UTC))`, mantendo a convenção de colunas UTC
  sem fuso já usada pelo projeto (`app/core/time.py`). Mesmo valor gravado.

## 5. Timeouts de câmera do OpenCV (alteração da rodada anterior, conferida)

- **Fonte:** `CAP_PROP_OPEN_TIMEOUT_MSEC` / `CAP_PROP_READ_TIMEOUT_MSEC`: "(open-only)
  … applicable for FFmpeg and GStreamer back-ends only" —
  <https://docs.opencv.org/4.x/d4/d15/group__videoio__flags__base.html>
- **Conclusão:** passá-los na abertura (`VideoCapture(source, CAP_ANY, params)`) está
  correto. Com outros backends o timeout não vale; por isso a chamada continua em
  `asyncio.to_thread` para não travar o event loop.

## 6. Limites de hospedagem e banco (confirmação, sem mudança de código)

- Vercel Functions: Python até 500 MB descompactado; corpo de requisição/resposta até
  **4,5 MB** (413 `FUNCTION_PAYLOAD_TOO_LARGE`); duração padrão 300 s —
  <https://vercel.com/docs/functions/limitations>. O limite interno da API
  (`REQUEST_MAX_BODY_BYTES`, padrão 64 MiB) é maior que o da plataforma, então lotes
  grandes de frames chegariam como 413 da Vercel. **Hipótese a medir:** tamanho real dos
  payloads de cadastro/identificação em aparelho de obra.
- Supabase: "Transaction mode does not support prepared statements … turn them off" e
  "Set the pool to 1 connection" para serverless —
  <https://supabase.com/docs/guides/database/connecting-to-postgres>.
  `app/db/session.py` já usa `NullPool` e desativa caches de prepared statements no
  pooler; nada a mudar.
